# 项目管理完全重构方案

本方案以当前源码及独立测试库证据为基础。目标是让项目服从本地文件管理习惯，并统一任务、动态、交付、恢复和专注的归属。当前已有大量实现，但尚未完成整体验收；不能承诺不存在任何缺陷。

## 一、统一产品规则

1. 项目是一个普通文件夹，通过其中的项目主页 `.home` 登记。普通资料不必改成插件专用格式。
2. `projectId` 是身份，目录是当前位置；显示名称、分类、目录名彼此独立。修改分类不搬目录，修改显示名称不隐式重命名文件夹。
3. 用户可以在资源管理器中整理目录。下次发现唯一相同身份时更新位置，保留任务和历史；遇到重复身份、嵌套项目或多个主页，明确报告冲突，不静默选择。
4. 项目阶段由用户决定，任务完成率由任务计算；两者不得互相覆盖。暂停项目不清空进度。
5. 查看与扫描不修改原资料。旧项目只在用户首次明确修改时建立身份并备份；原 Overview、Timeline 等笔记保留。

## 二、日常流程

首页只保留两个主要入口：新建项目、登记现有文件夹。新建仅要求名称，编号、分类和位置可选；没有分类也能开始工作。登记无需搬动资料。

项目页提供概览、任务、交付、动态、数据与恢复、文件六个固定入口。概览显示阶段、下一步、任务摘要和最近活动；操作后更新相关统计。高级维护集中到“项目检查与关联”，不让用户为常规操作理解内部索引。

任务默认只管理显式创建的项目任务，不自动吞入所有 Markdown 待办。关联文件使用项目内相对路径；内部已确认的改名更新关联，无法确认的离线改名显示缺失和重新关联入口。

交付默认使用项目内“交付物”，可以直接发布。交付 ZIP 与可恢复的项目迁移包分开命名和说明；发布记录失败后提供补登记已有包，避免重复打包。

## 三、目录变化与时间线

| 情况 | 处理规则 |
| --- | --- |
| 打开时在 Obsidian 内改名或移动 | 使用 Vault 确认的事件更新位置和可确定的文件关联 |
| 打开时在资源管理器整理目录 | 接收文件事件并重新核对；只在身份唯一、历史目标未被占用时迁移索引 |
| 关闭期间整理目录 | 启动后按稳定身份核对当前位置；扫描比较文件最终状态 |
| 关闭期间反复修改同一文件 | 只能发现最终差异，不能重建每次编辑与精确发生时间 |
| 复制整个项目 | 报告重复身份；用户选择作为独立副本后生成新身份 |
| 项目移出知识库或暂时不可见 | 保留缺失记录和历史，不当作用户明确删除 |

动态区分三类事实：插件明确提交的业务事件、实际保存的文件版本、启动核对发现的差异。核对记录标注“发现时间”，内容相同只给移动候选，不擅自认定改名。若未来要求关闭期间连续监控，需要另立常驻服务或版本控制集成，不能由插件本身假装实现。

## 四、数据与一致性

项目主页保存身份、属性、任务、里程碑及业务事件；位置、文件核对、版本内容和检查点使用独立索引。目录扫描是可重建的发现层，不能成为业务数据来源。

所有项目修改经同一存储入口串行执行：读取最新文件、校验、增量修改、校验最终数据，再比较原内容提交。过期表单和检测到的外部修改必须拒绝覆盖。成功保存与随后界面刷新失败分别反馈，防止用户重复提交。

离线文件改名确认按一次维护事务处理：先将历史/检查点路径迁移到新路径，再更新项目主页中的相对文件关联，最后写入文件核对的“已确认改名”审计。任一步失败都会使用带版本比较的回滚闭包恢复前一步；如果期间已有其他窗口、同步器或用户编辑，回滚也会拒绝覆盖并明确要求重新扫描。该机制保证插件进程内不会静默留下半迁移状态，但不能把外部同步软件变成支持多文件事务的锁。

索引损坏、历史内容校验失败或历史写入失败时停止相关历史操作并保留原文件。跨设备比较不是文件锁，也不是多文件事务；不得宣传为无条件解决同步冲突。

## 五、恢复与迁移

检查点恢复必须先展示覆盖、补回和保留范围，再建立安全检查点；默认保留后来新增的文件。项目主页恢复保留当前身份及已有操作记录，追加恢复事件。多文件可能部分成功，结果必须列明失败项。

检查点仅覆盖支持的文本，不包括图片、PDF 等完整资料备份。当前文本快照上限为单文件 1 MiB；发布源文件上限 256 MB，项目迁移包导入上限 512 MB。界面和文档必须说明这些边界。

迁移包包含项目文件与可选历史，导入仅允许新目录，预检路径、内容校验值、身份和历史引用。导入先写入插件私有暂存目录，项目主页最后发布；文件写入失败会清理暂存内容，不发布半成品项目；历史已经提交但主页发布失败时回滚新历史并清理目标目录，清理失败才明确报告保留位置。复制普通文件夹不会自动携带插件配置目录内的历史。

## 六、实施与放行顺序

1. 数据基础：稳定身份、只读发现、旧数据备份、统一增量保存、冲突拒绝。当前已实现并有模拟测试。
2. 日常闭环：创建/登记、属性、任务、阶段、文件关联、交付、统一动态、专注归属。当前已有实现，实机证据仍不完整。
3. 恢复闭环：检查点、项目移动后的恢复、交付补登记、含历史迁移、独立副本。不得仅凭服务测试放行。
4. 易用性：统一控件和反馈，浅色/深色、窄窗口、长名称和大量任务逐屏检查；概览摘要与各页数据一致。
5. 发布：只修复验收暴露的问题；所有必需流程通过后整理迁移说明和发布包，不把未验证项目标成完成。

逐项验收以[整体验收矩阵](./项目管理整体验收矩阵.md)为准。每项必须记录构建、测试库、操作、界面和磁盘结果。关闭期间移动、恢复、跨库导入、重复身份及真实同步冲突是独立场景，不能互相替代。

## 七、当前判断

当前方案已具备代码落地基础，`npm run check` 已通过；独立测试库已验证部分创建、目录移动、分类独立、任务完成/取消完成、动态去重，以及位置索引冲突的 fail-closed UI 提示（不会自动合并，恢复后可清除冲突）。检查点完整恢复、交付完整流程、跨库迁移、专注统计、多端界面和真实同步软件的并发冲突仍需按整体验收矩阵补齐。正式发布前以这些证据作为完成条件，不把确定性注入测试表述成已解决所有同步冲突。
